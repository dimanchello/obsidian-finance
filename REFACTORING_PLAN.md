# План рефакторинга Obsidian Finance Tracker → v1

Дата обновления: 2026-07-25
Базовое состояние: 12 520 строк TS, 58 тестов (4 файла), `npm run lint && npm run build && npm test` — зелёные.

## Рамки работы

Три установки, которые определяют весь план:

1. **Обратная совместимость не нужна.** Любые breaking changes допустимы. Публичных API нет, потребитель кода один — сам плагин.
2. **Миграции данных не нужны.** Плагином никто не пользуется. Формат на диске — это **v1** без предыстории: `DATA_VERSION = 1`, никаких `migrateLegacy` / `migrateToShortFolder` / полей-заглушек `??=` под старые схемы. Если формат окажется неудачным — меняем его молча, без миграции.
3. **Порядок обратный обычному: сначала самое сложное.** Крупные архитектурные вещи идут первыми, пока код ещё не оброс новыми деталями и пока есть запас внимания. Мелочь — в конце, потому что часть мелочи растворится сама при переписывании крупного.

Цель: современный, тестируемый код по best practice. Метрика — доля логики, покрываемой юнит-тестами без DOM, и отсутствие дублирования.

## Этап 1: Финансовое ядро — чистые функции и их тесты (самое сложное, делаем первым)

Это фундамент. Пока расчёты живут внутри `AccountView` и `storage`, их нельзя протестировать, а без тестов остальной рефакторинг — движение вслепую. Всё остальное в плане опирается на этот этап.

### 1.1. Починить арифметику дат — это баги, а не стилистика

Прежде чем выносить логику, надо её исправить, иначе перенесём баги.

**Баг A — сдвиг даты через `toISOString()`.** Проверено:
```
new Date(2026, 0, 31).toISOString().split('T')[0]  →  "2026-01-30"   // в TZ=Europe/Moscow
```
`toISOString` конвертирует в UTC, и локальная полночь становится предыдущим днём. Каждое начисление по вкладу и каждый платёж по кредиту датируются днём раньше. 8 мест.

**Баг B — переполнение месяца в `setMonth`.** Проверено:
```
d = new Date(2026, 0, 31); d.setMonth(d.getMonth() + 1)  →  2026-03-03
```
Вклад, открытый 31 января, получает начисления 3 марта, 3 апреля… — весь график съезжает. Банковское поведение — «последний день месяца, если такого числа нет», т. е. 28 февраля. 5 мест.

**Решение** — в `src/domain/dateMath.ts` две чистые функции, работающие со строками `YYYY-MM-DD` и никогда не выпускающие `Date` наружу:
```ts
export function addMonthsClamped(dateStr: string, months: number): string
// 2026-01-31 +1 → 2026-02-28;  2026-01-31 +13 → 2027-02-28

export function toDateStr(d: Date): string   // локальные геттеры, не toISOString
```
Тесты обязательны: конец месяца, февраль невисокосный/високосный, переход через год, отрицательный сдвиг. Затем заменить все 8 + 5 мест и **запретить `toISOString` линтером** (`no-restricted-syntax`), чтобы не вернулось.

### 1.2. Вынести денежную арифметику

Сейчас `Math.round(x * 100) / 100` разбросан по коду, а суммы копятся сложением float. `0.1 + 0.2 = 0.30000000000000004` — на длинном графике капитализации накапливается расхождение.

`src/domain/money.ts`:
```ts
export function round2(n: number): number
export function sumMoney(values: number[]): number   // округление на каждом шаге
```
Решение сознательно остаётся на `number`: переход на копейки-в-целых или decimal-библиотеку — это переписывание всех типов и всего ввода, что для личного плагина не оправдано. Фиксируем правило: **любая сумма, попадающая в хранилище, проходит через `round2`**.

### 1.3. Вынести график вкладов и кредитов в чистые функции

Ядро задачи. Сейчас это ~220 строк внутри `AccountView.checkAutoTransactions` (AccountView.ts:307-537), перемешанных с рендером, плюс `recalculateFutureAccruals` в storage.ts:793.

`src/domain/schedule.ts` — функции **без** `Date.now()`, без `crypto.randomUUID()` и без `new Date()` внутри: всё недетерминированное принимается параметром. Именно это делает их тестируемыми.

```ts
export interface ScheduleDeps {
  today: string;
  now: number;
  newId: () => string;
}

export function buildDepositSchedule(deposit: DepositRecord, deps: ScheduleDeps): DepositAccrual[]
export function buildCreditSchedule(credit: CreditRecord, deps: ScheduleDeps): CreditPayment[]
export function recalcFutureAccruals(deposit: DepositRecord, today: string): DepositAccrual[]
```

Заодно исправить `recalcFutureAccruals`: `lastPaid` считается через `filter().sort()` **внутри** цикла (storage.ts:805 и 819), т. е. O(N log N × M). Вынести до цикла → O(N log N + M). Это не только производительность — одинаковое значение, пересчитываемое на каждой итерации, само по себе признак того, что код просит вынесения.

**Тесты — главный результат этапа.** Раньше это было непроверяемо; теперь:
- вклад с капитализацией: сумма начислений == итоговая сумма минус тело;
- вклад «на счёт»: тело не растёт;
- открытие 31 числа → корректные даты всех N начислений;
- кредит: сумма платежей закрывает тело + проценты;
- досрочное погашение: пересчёт остатка;
- пополнение/снятие: будущие начисления пересчитаны, прошлые не тронуты.

### 1.4. Свести применение графика в один сервис

`src/domain/autoTransactions.ts` — функция, которая принимает состояние и возвращает **новое** состояние плюс список изменений, ничего не сохраняя и не рисуя:

```ts
export interface AutoTxResult {
  records: FinanceRecord[];
  deposits: DepositRecord[];
  credits: CreditRecord[];
  changed: { records: boolean; deposits: boolean; credits: boolean };
}

export function applyAutoTransactions(data: AccountData, deps: ScheduleDeps): AutoTxResult
```

Здесь же чинятся три дефекта, найденные в текущей реализации:

- **`depositsChanged = true` безусловно** (AccountView.ts:389) — стоит вне всех `if`, поэтому файл вкладов перезаписывается на каждом рендере даже без изменений. Флаг должен подниматься только при фактической мутации.
- **Дедупликация записей есть у кредитов, но не у вкладов.** Кредиты проверяют `records.some(r => r.linkedId && r.date && r.type)` (строки 465, 497), вклады — нет (строка 368). Правило одно для всех типов, ему место в этом сервисе.
- **Проверка «кредит выплачен» через `remainingAmount === 0`** (строка 523) — сравнение float с нулём. Заменить на «нет платежей в статусе pending».

После этого `AccountView.checkAutoTransactions` сжимается с ~230 строк до ~25: вызвать, записать, перерисовать.

### 1.5. Убрать вызов на каждом рендере

`checkAutoTransactions` вызывается из `render()` (строка 66) и `refreshAndRender()` (строка 206) — то есть при каждом переключении таба. Тяжёлая операция + до трёх записей на диск.

Правильное решение (не кэш-флаг, а корректная модель): проверка — это **событие**, а не часть рендера. Вызывать при открытии счёта и по таймеру раз в час; `render()` только рисует. Таймер регистрировать через `registerInterval` плагина, чтобы Obsidian снял его при выгрузке.

Здесь же появляется давно отсутствующий `AccountView.destroy()` — сейчас его нет вообще, и это причина утечек из Этапа 4.

**Результат этапа 1:** финансовая логика — чистые функции, покрытые тестами; два реальных бага в датах исправлены; `AccountView` перестал быть носителем бизнес-логики; диск не пишется на каждом рендере.

### 2.2. Идентичность счёта: `accountId` в код-блоке вместо пути к заметке

Самое важное изменение в слое данных. Сейчас **путь к заметке — это идентичность счёта** (`CLAUDE.md`: «one note = one account»), и из этого растут все проблемы с перемещением.

#### Почему хеш от пути — плохая идея (отказываюсь от своего же предложения)

Хеш решает коллизии имён, но задачу «заметку переместили» **не решает вообще**: `hash("Finance/Основной.md")` и `hash("Архив/2026/Основной.md")` — разные значения. При перемещении папка данных всё равно должна быть переименована, то есть нужен тот же самый хрупкий обработчик `rename`, что и сейчас. Хеш лишь делает имя папки нечитаемым, ничего не давая взамен.

Корень проблемы глубже: **идентичность привязана к тому, что пользователь вправе менять в любой момент.** Пока это так, любая схема имён требует перехвата всех переименований и перемещений — и молча ломается на всём, что перехватить нельзя.

#### Решение: идентификатор живёт внутри код-блока

Параметр `source` обработчика код-блока сейчас не используется (`main.ts:21` — принимается и игнорируется). В него и надо положить идентичность:

````markdown
```finance-account
id: a7f3c92b4e1d
```
````

Папка данных — `accounts/a7f3c92b4e1d/`. Она **никогда не переименовывается**, потому что не зависит ни от чего внешнего.

Что это даёт по вашему требованию:

| Действие пользователя | Сейчас | После |
|---|---|---|
| Переименовать заметку | обработчик `rename` переименовывает папку | ничего не происходит — и не нужно |
| Переместить в другую папку | то же, и ломается при коллизии имён в новой папке | ничего не происходит |
| Переместить вместе с родительской папкой | событие приходит на папку, не на файл → **данные брошены** | ничего не происходит |
| Переименовать вне Obsidian (файловый менеджер, git pull, синхронизация) | событие не приходит → **данные брошены** | ничего не происходит |
| Скопировать заметку целиком | две заметки делят одну папку данных, при этом `folderOverrides` разведёт их случайным образом | обе показывают один счёт — предсказуемо |

Последние две строки — главный выигрыш. Их **невозможно** починить в рамках «путь = идентичность», потому что события просто не доходят: Obsidian присылает `rename` на перемещённую папку, а не на каждый файл внутри, а изменения на диске мимо Obsidian он не видит вовсе.

Идентификатор едет вместе с заметкой автоматически: он находится **внутри** её содержимого. Ни одного обработчика событий для этого не требуется.

#### Как выдаётся идентификатор

При первом рендере блока без `id`:
1. сгенерировать `id` (12 hex-символов от `crypto.randomUUID()`);
2. вписать его в код-блок через `vault.process(file, …)` — атомарное чтение-изменение-запись, доступно с Obsidian 1.1.0 (в проекте типизации 1.12.3, `minAppVersion` 1.4.0 — проходит);
3. точное место блока в файле дать `ctx.getSectionInfo(el)` → `lineStart`/`lineEnd`, чтобы правился именно этот блок, а не первый совпавший по тексту.

Запись в заметку из обработчика рендера вызовет повторный рендер, поэтому нужен guard: множество уже обслуженных `docId` + проверка, что `id` в источнике отсутствует. Пишем один раз за время жизни блока.

Краевые случаи, которые надо закрыть явно (иначе они станут багами):
- **`getSectionInfo` вернул `null`** — бывает для встроенных/экспортируемых представлений, где заметка недоступна на запись. Не падать: отрендерить счёт в режиме «только чтение» с пометкой и повторить попытку при следующем рендере. Молча создавать безымянный счёт нельзя — он станет мусором.
- **`id` испорчен руками** (не подходит под `/^[0-9a-f]{12}$/`) — показать явную ошибку в блоке, не подставлять новый молча: иначе опечатка в одном символе тихо отвяжет счёт от его данных.
- **Два блока с одним `id`** (заметку скопировали) — считать это нормой: один счёт, два представления. Кэш в `AccountRepo` ключуется по `accountId`, поэтому оба вида читают одно состояние и не расходятся. Отдельно проверить, что запись из двух видов одной заметки не теряется.
- **Несколько блоков в одной заметке** — теперь это разные счёта (раньше оба были одним, так как ключ был путь). Полезная возможность, но проверить.
- **Заметку удалили** — папка остаётся. Это лучше, чем удалять финансовые данные по событию удаления файла (`rename`-события и так теряются, а восстановить удалённое неоткуда). Добавить команду «найти брошенные счёта», показывающую папки, чей `id` не встречается ни в одном код-блоке vault, с возможностью удалить вручную.

#### Что из кода уходит

- Обработчик `vault.on('rename')` в `main.ts:41-56` — **целиком**, вместе с ре-ключеванием `localStorage`.
- `FinanceStorage.renameAccount()` — `storage.ts:888-938`, 51 строка перекладывания кэшей и dirty-множеств.
- `folderOverrides` (строка 55) и весь механизм разрешения коллизий в `ensureNoteFolder` (93-122).
- `getFolderBaseName()` (68-75) — имя больше ни из чего не выводится.
- `AccountMetaFile.sourcePath` как признак идентичности. Поле остаётся, но становится подсказкой «где заметка была замечена последний раз» — для команды поиска брошенных счетов и для отображения. На поведение оно больше не влияет.

`notePath` перестаёт быть ключом: 318 упоминаний в 8 файлах меняются на `accountId`. Механическая, но обширная замена — поэтому идёт **до** этапа 3, пока табы ещё не переписаны, чтобы не делать её дважды.

#### Существующие данные

Формально миграции не нужны (v1, пользователь один). Но именно из-за смены схемы имён папка старого счёта окажется брошенной, а вы просили этого избежать. Дешёвый разовый вариант: при первом рендере блока без `id` проверить, существует ли папка с прежним именем (по старому правилу «два последних сегмента пути через `_`»); если да — переименовать её в `accounts/<новый id>/` и вписать `id` в блок. Это ~15 строк в одном месте, без каркаса миграций и без версий. После первого запуска на всех своих заметках — удалить.

Если данных не жалко — шаг можно пропустить целиком, плагин создаст пустые счёта.

### 2.3. Разделить storage на слои

941 строка смешивает четыре обязанности: пути в vault, кэш, дебаунс записи, финансовые пересчёты (`recalculateFutureAccruals` — уже уехал в Этап 1.3).

```
src/storage/
├── VaultAdapter.ts    — read/write/exists/rename + atomicWrite; единственное место, знающее про app.vault
├── AccountFiles.ts    — раскладка папок; после 2.2 это тривиальный `accounts/<id>/<file>.json`

```

Ключевое упрощение: сейчас пять почти одинаковых пар «кэш + dirty-множество» (строки 40-53) и пять почти одинаковых блоков во `flushDirty` (485-531). Это одна обобщённая сущность с пятью экземплярами, а не пять сущностей.

Плюс: `AccountRepo` инжектируется, значит тесты storage перестают патчить `app.vault.adapter` руками.

### 2.4. Одно состояние вместо двух

Сейчас `ViewState` пишется **дважды** — в `localStorage` и в `state.json` (`context.ts:68-73`), а читается в два приёма: синхронно из `localStorage` в конструкторе, потом асинхронно из файла с наложением поверх (`AccountView.render` строка 56). Два источника истины, которые расходятся при внешнем изменении.

Оставить `state.json` (переживает переустановку, живёт рядом с данными, а после 2.2 ещё и корректно едет вместе со счётом). `localStorage` — убрать целиком; ре-ключевание при переименовании в `main.ts:45-52` уходит вместе с самим обработчиком `rename`.

## Этап 3: UI-слой

### 3.1. Обобщить табы

Главная по объёму задача: ~1 900 строк дублей на 4 621 строку.

Решение — **не наследование, а конфигурация**. Абстрактный `BaseTab` с полутора десятками protected-методов на четыре наследника даёт связность, которую сложно тестировать. Лучше описание таблицы данными + один универсальный рендерер:

```ts
export interface TableSpec<T, F> {
  columns: ColumnSpec<T>[];
  filter: FilterSpec<F>;
  sortFields: SortFieldSpec<T>[];
  rowActions: (item: T) => ActionSpec[];
  stats: (items: T[]) => StatCard[];
  stateKeys: { page: string; sort: string; filter: string; columns: string };
}

export function renderDataTable<T, F>(host: HTMLElement, spec: TableSpec<T, F>, ctx: ViewContext): void
```

Тогда каждый таб — это спецификация (~150-200 строк вместо 1 000-1 300), а весь общий механизм (пагинация, bulk-select, видимость колонок, панель фильтров, мобильные карточки, таблица) живёт в одном месте и тестируется один раз.

Порядок — от простого к сложному, чтобы форма спецификации устоялась на дешёвом кандидате:
1. `renderDataTable` + спецификация для `RecordsTab` (самый простой);
2. `DebtsTab` — проверка на самом непохожем (движения, направление, `person`);
3. `CreditsTab` и `DepositsTab` — они структурно идентичны (по обследованию отличаются только литералом статуса `active|paid` vs `active|closed`), поэтому после первых двух идут почти механически.

Что остаётся индивидуальным и должно оставаться подключаемым: разворачиваемые панели (`renderDebtMovementsPanel` 33 строки, `renderCreditPaymentsPanel` 139, `renderDepositAccrualsPanel` 183) и производные-хелперы (`getDebtRemaining`, `getDepositProfit` и т. п.) — они реально разные, их не трогаем.

Заодно исчезает необходимость в кэшировании фильтрации из старого плана: фильтр применяется один раз за рендер в одном месте: незачем.

Отдельно: `renderRecordsTab`/`renderDebtsTab`/… в `AccountView.ts:161-201` содержат бессмысленное `if (!this.tab) new Tab() else new Tab()` — обе ветви одинаковые. Убрать вместе с неиспользуемыми полями `recordsBodyEl`/`debtsBodyEl`/`creditsBodyEl`/`depositsBodyEl`.

### 3.2. Один Combobox вместо пяти

Пять реализаций одного виджета: `RecordModal.buildAutocomplete` (~65 строк, внутри переиспользуется 3 раза), `DebtModal` (~60), `CreditModal` (~55), `DepositModal` (~55) и `mkSearchSelect` в табах (91-103 × 4).

`src/ui/Combobox.ts` — один компонент, покрывающий объединение возможностей: фильтрация, клавиатура (Enter / Escape / ArrowUp / ArrowDown), опциональный пункт «создать `"запрос"`» (сейчас есть только в `DebtModal`), пустое состояние, корректное закрытие. Текущее закрытие через `setTimeout(close, 150)` — гонка; заменить на `focusout` с проверкой `relatedTarget`.

Экономия ~400 строк и, что важнее, одинаковое поведение во всех местах — сейчас в двух вариантах `mkSearchSelect` по-разному работают клавиши.

### 3.3. Инпут суммы — один компонент

Блок focus/input/blur с сохранением позиции курсора при переформатировании — ~40 строк, повторён **9 раз** (~360 строк). `src/ui/AmountInput.ts`, один раз и с тестом на позицию курсора.

Туда же `src/ui/DateField.ts` для 18 мест с датой/временем.

### 3.4. Инфо-модалки

`InfoModal` (66), `DebtInfoModal` (65), `CreditInfoModal` (66) — почти один и тот же файл; в них же 54 инлайн-стиля из 290. Свести к одному `InfoModal`, принимающему список секций.

### 3.5. Инлайн-стили → CSS

~290 присваиваний `.style.X`. Механическая работа, но с реальной пользой: инлайн-стили не переопределяются темами Obsidian, а плагин обязан выглядеть уместно в любой теме.

Порядок по концентрации: `DepositsTab` (59) → `CreditsTab` (44) → `AnalyticsView` (30) → инфо-модалки (54 на три файла) → остальное. Исключение — значения, вычисляемые в рантайме (ширина полосок в аналитике): для них CSS-переменные, а не классы.

Оставить `setProperty('--ft-accent')`, но починить: `applyAccentColor('')` ставит пустую строку вместо удаления свойства. Нужен `removeProperty` при пустом значении.

### 3.6. Убрать `innerHTML`

13 присваиваний в 7 файлах. Подтверждённых XSS-стоков нет — интерполируются только i18n-строки, а единственное место, близкое к пользовательским данным (`DebtModal.ts:127`, пункт «создать») уже сделано через `textContent`. Но `innerHTML` с интерполяцией — это ожидающий своего часа баг: достаточно одному месту начать подставлять имя категории. Заменить на `createEl`/`createSpan` и запретить линтером.

## Этап 4: Мелочь и полировка (в конце — часть уже растворилась выше)

Что осталось после этапов 1-3. Оценки честные: это правда мелочь.

### 4.1. Утечки слушателей — 20 минут
`document.addEventListener('click', …)` в `renderHeader` (`AccountView.ts:129`) навешивается на каждый рендер и не снимается никогда. То же в `renderCurrencyBadge` (272-278). Снимать в `AccountView.destroy()`, который появился в Этапе 1.5, — или, что чище для Obsidian, регистрировать через `Component.registerDomEvent`.

### 4.2. Импорт: всё не-income считается expense — 15 минут
`ImportExportModal.ts:414`:
```ts
type = tv.toLowerCase() === this.typeMap.incomeVal.toLowerCase() ? 'income' : 'expense';
```
Опечатка в CSV молча становится расходом. Сверять с `typeMap.expenseVal` (поле уже есть, строка 117) и пропускать строку с неизвестным типом, сообщая счётчик пропущенных.

### 4.3. Мёртвый параметр `payment?` — 5 минут
`CreditPaymentOptions.payment?: CreditPayment` (`CreditPaymentModal.ts:9`) объявлен и нигде не читается — проверено. Удалить: редактирование платежа как фича не заявлено, а неиспользуемое поле в интерфейсе обещает то, чего нет.

### 4.4. CSV с переводами строк внутри кавычек — 1 час
`parseCSV` (`ImportExportModal.ts:191-217`) режет вход по `\r?\n` до разбора кавычек, поэтому поле `"строка1\nстрока2"` ломает файл. Нужен посимвольный проход с флагом `inQuotes` (RFC 4180). Без внешней библиотеки — задача на час, а `papaparse` в бандл плагина тянуть незачем.

### 4.5. ISO-неделя — 20 минут
`AnalyticsView.getWeekNumber` не соответствует ISO-8601 (неделя не с понедельника, первая неделя года определяется иначе). Правильный алгоритм — 5 строк, ему место в `src/domain/dateMath.ts` из Этапа 1.1, с тестом на 1 января в разные дни недели.

### 4.6. Пагинация: ограничить число кнопок — 30 минут
При 100 страницах создаётся 100 DOM-узлов. Показывать `1 … 48 49 [50] 51 52 … 100`. После Этапа 3.1 правится в одном месте вместо четырёх. `PAGE_RANGE_THRESHOLD` в `types.ts:163` уже есть.

### 4.7. Ужесточить tsconfig — 30 минут + правки
Сейчас включён только `strictNullChecks`, при этом ESLint работает в режиме `strict-type-checked` — то есть линтер строже компилятора. Включить полный `"strict": true` плюс `noUncheckedIndexedAccess`, `noImplicitOverride`, `exactOptionalPropertyTypes`. Это вскроет реальные проблемы (обращения по индексу без проверки), поэтому идёт **после** крупного рефакторинга — иначе будем править код, который всё равно переписывается.

Здесь же — `no-restricted-syntax` на `toISOString` (Этап 1.1) и на `innerHTML` (Этап 3.6), чтобы исправленное не вернулось.

## Риски

**Этап 1 меняет расчёты — и это заметно.** Исправление `toISOString` и `setMonth` сдвинет даты в уже существующих графиках. Это исправление бага, но выглядит как «плагин переписал мои данные». Митигация: перед этапом сохранить копию папки `accounts/`, после — сверить один вклад и один кредит вручную. Пользователь один, предупредить его — тривиально.

**Этап 2.2 пишет в заметки пользователя.** Плагин впервые начинает изменять `.md`-файлы, а не только свою папку. Это самое серьёзное новое поведение во всём плане: ошибка в определении границ блока испортит содержимое заметки. Митигация: правка строго по `lineStart`/`lineEnd` из `getSectionInfo`, только через `vault.process` (атомарно), только когда `id` отсутствует, и с guard-множеством против повторного срабатывания на самостоятельно вызванный ре-рендер. Перед первым запуском — копия vault. При `getSectionInfo() === null` не писать вообще.

**Смена схемы имён папок — разовая точка невозврата.** Старые папки перестают находиться. Закрывается разовым шагом «подхватить папку по прежнему правилу» из 2.2 (~15 строк), но выполнить его нужно **до** того, как заметки будут перемещены, иначе прежнее имя уже не выводится из текущего пути. Практически: сделать этап 2.2 и сразу открыть все свои finance-заметки на прежних местах.

**Этап 2.2 меняет 318 упоминаний `notePath` в 8 файлах.** Механически, но широко. Делать до этапа 3, иначе замена пройдёт по коду табов дважды. Компилятор поймает почти всё, если переименовать тип: не `string` → `string`, а ввести `type AccountId = string & { readonly __brand: unique symbol }` хотя бы на время рефакторинга — тогда любое место, где перепутаны путь и id, станет ошибкой сборки, а не тихим багом.

**Этап 3.1 — самый объёмный.** Абстракция может оказаться неудачной: `TableSpec` может не покрыть все четыре случая. Именно поэтому порядок «Records → Debts → Credits/Deposits»: `DebtsTab` — самый непохожий, и если спецификация ломается, это выяснится на втором шаге, а не на четвёртом. План Б — оставить `DebtsTab` со своим рендером, а обобщить три остальных; выигрыш всё равно ~1 200 строк.

**Тесты покрывают только логику.** По конвенциям проекта DOM и модалки не тестируются, а этап 3 — почти целиком DOM. Значит его страховка — ручная проверка по списку выше, и её нельзя пропускать. Для новых UI-компонентов (`Combobox`, `AmountInput`) чистую логику — фильтрацию опций, форматирование, позицию курсора — всё же вынести отдельно от DOM и покрыть тестами.
